# Kosa 形式化工作手冊

這份 skill 是 Kosa 工程的記憶。每次開工先讀完本文件，再按需讀 `references/` 下的文件。
工作中學到的新東西（新讀法、踩到的坑、改了的約定），當輪就寫回這裡——這是唯一能留到下一個對話的東西。

## 零、開工

1. 取倉庫：add_repo（owner `wanglu2016`，repo `kosa`，access `push`），照工具的提示 clone 並 register_repo_root。
   《俱舍萬字》原文在 `wanglu2016/abhidharma` 的 `src/wanzi.json`（只讀即可）。
2. 讀倉庫中的 `.claude/skills/kosa-formalize/` 全部文件（這份 SKILL 的正本與 `references/`）。賬戶裡的這份只有 SKILL.md，參考文件以倉庫為準。
3. `pip install --break-system-packages clingo fonttools brotli lzstring`，跑一遍 `python3 -m kosa 驗證`，確認起點是綠的。
4. 看 `references/待辦.md` 的「下一輪從這裡接著做」。

## 一、目標與分工（作者王路的要求，2026-11）

- **目標**：把有部公認的阿毘達磨命題形式化，建成一個像 Mathlib 那樣的基礎設施。建好之後，任意一條阿毘達磨命題的背景都已在庫中，可以寫成嚴格的命題，交給機器檢驗、交給 AI 證明。
- **主要成果之一**：逆推出阿毘達磨的基礎施設有多少、是哪些。哪些命題作施設，不是前提，而是要在實踐中探索的結果。
- **分工**：形式化、判斷命題是否成立、選施設、寫證明，都由 Claude 做。作者是阿毘達磨專家，不熟形式化工具；**盡量不找作者討論**，只在極少數真正無法判斷時才問。發現矛盾，自己定位、自己修正。
- **範圍**：只取有部公認的說法，暫不考慮異說（婆沙異說、經部、正理與俱舍的分歧）。《俱舍九題》第九題眾賢之矛盾一類難題，優先級很後。
- **用語**：做阿毘達磨工程，盡量用阿毘達磨的表述：說「有情」不說「人」，說「施設」「所依」「所緣」等。

## 二、幾條根本原則

1. **命題是原子。** 庫的基本單位是一條命題，不是一頌、一句論文。一頌往往不止一個命題，常要補限定，或有例外。頌是很好的命題來源和組織結構，可作重要參考，但不直接作原子。
2. **先引頌。** 碰到任何問題，先想《俱舍論頌》裡哪一頌（或哪幾頌）能直接回答它，到 `語料/俱舍論頌.json` 查出原文並引用。例：「無漏靜慮不因上生而捨」→ 業品「捨定生善法，由易地退等；捨聖由得果，練根及退失」；「得而未捨則成就」→ 根品「得謂獲成就」。背景常常分散在別品，不在結論所在的那一品。
3. **翻譯與限定是最難的一步。** 自然語言的阿毘達磨命題要先讀對，再寫成形式。例：「阿那含必然成就初靜慮」的嚴格意思是「阿那含不可能一種初靜慮都不成就」（味、淨、無漏三種之一），不是「成就一切初靜慮」。這類讀法收在 `references/讀法凡例.md`，照它翻譯，學到新的就補進去。
4. **成立與施設是兩件事。** 一條命題是否成立（有部是否承許）由阿毘達磨知識判斷；它是施設還是推出，由機器計算。不要因為推不出就把一條公認的命題標成「待核」，也不要把一條公認的規則按機制拆成幾種情況、再把其中一種標成待核（模組六的教訓，見 `references/坑.md`）。
5. **公認背景按論書自己的粒度寫。** 毘曇論證常是「直接理由＋公認背景」，背景不說出來。形式化要把背景按論書視為「已成立」的粒度寫出來，不必挖到機制；挖到機制可以以後做，不是前提。
6. **庫是基礎設施。** 公認背景往往是一整個框架。先建框架（概念、分類、門分別），再建命題；新命題的背景應當已經在庫裡。
7. **證據等級要說清楚。** 求解器只窮盡有限世界（命題庫至多 5 個法、2 個有情）：「證成」「推得出」是有界結論；全稱部分的「推不出（附反例）」是確定的。重要的推出要有 Lean 證明。
8. **存在命題逐條考。** 庫中含「有……」的命題（容有、通、各容有）自動拆成全稱部分「編號・全」與存在部分「編號・有1」……。全稱部分合起來是底子 U；存在部分逐條與 U 合考（有界世界裝不下上百條存在命題）。所以「未決」只表示「U 加任一條相關存在部分都判不出」，不是確定的。
9. **用題網量完備。** 對一個分類系統地出題（如九十八隨眠的 10×3×5 格），看庫是否每格都判得出。未決的格子告訴你缺甚麼。
10. **以題養庫。** 作者出題 → 先憑阿毘達磨知識解答（引頌）→ 把答案寫成題網入題庫 → 判不出就補本體與命題，直到每格一致 → 答案條目寫「依」並給 Lean 證明。補進去的應是可重用的背景（門、定義、按論書粒度的命題），不是為一題特設的捷徑；每補一條，問一句「別的題也會用到它嗎」。

## 三、逐條形式化的流程（批量時也每條照走）

批量處理最容易出三種錯：同一詞在不同條目裡讀法漂移；默認值悄悄補進去（「系」「生」「現起」不分）；一條讀法錯了，一批跟著錯。所以批量時把每條當作單條處理，照下面七步：

1. **找頌。** 在語料中找直接相關的頌，逐字引用（寫入「頌」欄，機器會核對 CBETA）。沒有頌的，記出處（《萬字》段號、《九題》頁碼、論名卷數）。
2. **列讀法。** 寫下這句話可能的嚴格讀法：量詞（凡、有、唯、通）、範圍（法還是有情；系、地、生、現起、成就哪一個）、類名是「其中一種」還是「全部」、有無例外。
3. **按凡例取捨。** 依 `references/讀法凡例.md` 選一種；凡例沒有的，按阿毘達磨義理定，並把新規則補進凡例。取捨理由寫入「詮釋」欄。
4. **寫成 Kosa 命題**，一條一個意思。用已有的詞；缺概念就先補本體（門、定義、關係），見 `references/格式.md`。
5. **自查。** `python3 -m kosa 判定 "命題"` 看它現在是證成、證否還是未決；未決時看引擎給的實例與反例世界是否合理。荒唐的實例說明還缺排除它的命題。
6. **入庫後全庫檢查。** `python3 -m kosa 驗證`（相容、推導、題庫）；`python3 -m kosa 結構`（新條目是施設還是推出，有沒有讓別的條目變成可推出）。出現矛盾：取極小衝突集，從出處最弱、把握最小的條目查起，多半是讀法錯了；修正讀法規則，重查用到這條規則的條目。
7. **記錄。** 新讀法 → 凡例；踩到的坑 → 坑；未做完的 → 待辦。

## 四、條目怎麼寫（速查；詳見 `references/格式.md`）

```
【根品15】凡 x、y：相應(x，y) ⇒ 性(x)＝性(y)
　標題：相應的心、心所同性
　頌：（逐字引頌，可多句，以「；」分隔）
　出處：《俱舍萬字》1.2.12；《俱舍九題》頁 26
　依：根品14、業品3、〔本體：性由、性・互斥〕   ← 可選：編者擬的推導，機器檢驗推得出、缺一不可
　詮釋：形式化時做的、原文沒明說的決定
　狀態：待核                                   ← 只在把握不足時標
　原編號：根定二（v0.4）
```

- 編號：品名＋序數（界品、根品、世間品、業品、隨眠品、賢聖品、智品、定品），接著該品最大的序數往下編。序數不表示層級。
- 不寫「層」。施設與推出由 `python3 -m kosa 結構` 計算。
- 「依」裡的本體條目寫在〔本體：…〕中：定義名（如「染」）、本體結構條目（如「性・互斥」「相應・類型」）。推不出時，`驗證` 會告訴你「再補哪些就推得出」。
- 句式：`A 唯 B`、`A 非 B`、`A 即 B`、`A 通 B、C`、`A 容 B`、`A 容有`、`A 無`、`A：B、C`（A 恰是 B、C 之和）、`B、C、D 互斥`、`B、C、D 各容有`；不夠用時寫公式 `凡 x、y：…⇒…`。
- 《萬字》的條目，「出處」寫「《俱舍萬字》1.1.11」並引原句；名目（列舉、定義）寫進 `本體/定義.kosa`，也標出處。

```bash
pip install --break-system-packages clingo fonttools brotli lzstring
python3 -m kosa 驗證        # 頌文核對、推導檢驗、全庫相容、題庫（相違才算錯）；約 2 分鐘

```

## 六、Lean

- 本機（雲端工作區）**裝不了 Lean**：網絡策略擋住工具鏈下載（403）。不要重試，也不要繞路。Lean 的檢查交給 GitHub Actions：推一個分支，用 `gh run list -R wanglu2016/kosa`、`gh run view <id> --log-failed` 看結果。
- 證明寫在 `lean/Kosa/Proof*.lean`，定理名必須是「«編號成立»」，前提恰是「依」中的條目編號（本體定義與結構條目在 Lean 中是內建的，不寫）。`Check.lean` 自動檢驗這一點。
- 改了命題文字，先 `python3 -m kosa lean` 重新導出，再改證明。
- `Lib.lean` 只有一個 `«世界»`，兩個載體 `W.«法»`、`W.«有情»`；門是 `W.«門» x`，關係是 `W.«成就» p x`。本體的適用條件、關係的類型與對稱在 `«本體公理» W` 裡（用 `O.«適用_律儀種» x` 一類取用）；門的互斥、窮盡是 inductive 自帶的。
- 新證明開一個新文件 `lean/Kosa/ProofN.lean`（`import Kosa.Proof4` 可用其中的小引理），在 `lean/Kosa.lean` 加 import；`python3 -m kosa lean` 會把它收進 Check.lean。
- 好用的寫法（Proof7 一次通過）：先證「某門有值則是某類法」一類小引理（`by_cases` ＋ `O.«適用_X»`）；把一個類的成員歸結為各門的值（如「諸律儀之體」給出法類、色自性、心所自性、六識四個值），再對假設 `simp only [定義名] at h` 展開、`rcases` 分情況，每種情況用 `first | (rw [h1] at h; cases h) | …` 收掉。兩個不同的門值相等，`cases` 直接收掉；`≠ .«—»` 用 `by rw [h]; decide`。
- 分支上 CI 只跑檢驗與 Lean（約 3 分鐘）；看結果：`gh run list -R wanglu2016/kosa --branch 分支名`，日誌中應有 `Built Kosa.ProofN` 與 `Built Kosa.Check`。

## 七、Git 與發佈

- 不在 main 上直接改：開分支、推送、開 PR，請作者合併；作者明說「merge」時，用 REST 合併：`gh api -X PUT repos/wanglu2016/kosa/pulls/N/merge -f merge_method=merge`（GraphQL 被擋）。GitHub Pages 只從 main 發佈報告。
- 合併前先在本機完整跑一次 `python3 -m kosa 報告`：分支上的 CI 不生成報告，報告的錯只會在 main 上暴露。
- 案例頁：`kosa/case.py`。一組作者出的題做完，可照它寫一頁（解答原文、讀法、題網、補庫、推導、Lean、判定示例），內容盡量從庫中當場讀出。
- 提交信息和 PR 描述按當前對話的署名要求結尾。
- CI 流程：`.github/workflows/kosa.yml`。Lean 或驗證失敗都會標紅，但報告照樣生成。
