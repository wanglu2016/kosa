# 坑與錯誤檔案

每條：現象 → 原因 → 怎樣避免。新的加在最前面。

## 形式化（阿毘達磨方面）

**「現起、繫」與「成就」混用，答案差一倍（三道題，v0.6）。** 「幾地有樂受」三地，「生幾地容成就樂根」九地。若把「成就樂根」讀成「現起樂受」或「有該地所繫的樂受」，就會答三地。→ 讀法凡例讀十八；有情與法之間用「成就（有情，法）」關係，不要用「生X ⇒ X地的法」一類捷徑。

**同名而體不同（律儀）。** 「律儀」可指無表律儀（色），也可指意根律儀（慧、念，心所）。只取前者，行蘊就「沒有律儀」了。→ 讀法凡例讀十六；遇到「任何」「一切」，先查這個名稱還指哪些法。

**把公認的規則拆成機制再標待核（模組六，v0.3）。** 證「阿那含必然成就初靜慮」時，把「已離欲染的聖者成就無漏初靜慮」按入見道所依之地拆成幾種情況，其中「先離欲染、依未至入見道」一種標了待核（智品2）。作者指出：直接理由是「阿那含必成就無漏法，又必已離欲染」，背景是「無漏靜慮不因上生而捨」，有頌可據（業品「捨聖由得果，練根及退失」）。
→ 先找頌；公認的規則按論書的粒度寫成一條；「是否公認」與「能否推出」分開。

**頌不是原子。** 一頌常含幾個命題、要補限定、有例外。→ 一頌拆成幾條命題，各引同一頌。

**憑記憶引頌，常錯字，甚至整句錯。** 例：「等起有二種，謂因及剎那」實為「等起有二種，因及彼剎那」；「色不見所斷」實為「色定非見斷」；「應知諸無表，律不律俱非」實為「無表三律儀，不律儀非二」；「意識通二種，五識唯隨轉」實為「唯隨轉五識，修斷意通二」。→ 頌一律從 `語料/俱舍論頌.json` 查出再抄，`驗證` 會核對。

**分詞吞字。** 詞表按最長匹配分詞。單字詞（如把十六行相的「苦」「集」「行」立為門值）會把別的詞切碎，報錯也看不懂。→ 名稱加後綴（「苦行相」）。

**重名。** 三界的「色界」與十八界的「色界」同名。→ Kosa 中「色界」只指三界之一；十八界之色界用「色處」。新詞入表前先查重。

**系、地、生、現起不分。** 「二定以上無眼識」若寫成「有情生二定則無眼識現起」就錯了。→ 讀法凡例讀九。

**列舉不等於劃分。** 《萬字》「A：B、C」只說 A 是 B、C 之和；四諦就不互斥。→ 劃分另立「互斥」一條。

## 引擎與工具

**改引擎時誤刪常量，驗證照樣全綠（v0.6）。** 改 `tree.py` 時把 `GOAL_LIMIT` 一行連同舊代碼刪了；`驗證` 不跑模組四的目標樹，沒發現；直到跑報告才報 NameError。若直接合併，main 上的報告就生成失敗。→ 改了 Python 就跑 `python3 -m pyflakes kosa/*.py`（看 undefined name），合併前完整跑一次報告。

**後台跑報告，子進程被殺（v0.6）。** 在一次 Bash 調用裡用 `( … ) &` 或 `nohup … &` 啟動 `python3 -m kosa 報告`，調用一結束進程就沒了，日誌是空的。→ 用 Bash 工具的 `run_in_background: true`，等它結束的通知再往下走。查進程用 `pgrep -af "kosa"`：`ps aux | grep 報告` 找不到，因為 ps 把中文命令名顯示成 `??????`；也不要讓兩次運行寫同一個日誌文件。

**對話壓縮後，自己先前發給作者的長文找不回來。** 第一部分的解答是用 SendUserMessage 發的，沒有存文件；對話被壓縮後原文丟失，做案例頁時只好按同樣的結論與理由重寫。→ 發給作者、以後可能要再用的長文（解答、說明），同時寫一份到倉庫或工作目錄。

**只依〔本體〕的條目從不檢驗（v0.6 修）。** `tree.verify` 原先只在條目有普通「依」時才檢驗推導；「依」只列〔本體：…〕的（業品31–33）從未被查。輔助腳本也有同樣的過濾。→ 改為：推導、目標節點只要有任何「依」就檢驗。寫腳本篩選推導節點用 `n.kind=='推導'`，不要用 `n.deps` 是否非空。

**依中有許多存在命題，推導檢驗空真通過（v0.6 修）。** 賢聖品12 依賢聖品10（八條「生X・聖者 各容有」）：八個有情裝不進 2 個有情槽，前提整體不可滿足，「推得出」空真成立。→ `tree._edge_ok`：依中的存在部分不再一起放進世界，而像判定一樣，對結論的每個部分，用 U 加至多一條相關存在部分去推。結論本身含多個「有」時也逐部分查。

**大地法十個，世界只有 5 個法（又一次碰到懸崖）。** 想寫「凡心皆有十大地法相應」，一個心聚就要 11 個法。→ 根品24 只寫「凡心皆有思相應」（第一題只需要思）。其餘九個大地法等將來按需要一條一條加，每加一條估一次元素數。

**Lean：跨論域關係要一個世界（v0.6）。** v0.5 法與有情各導出一個世界（Lib、LibP），「成就（有情，法）」無處可放。→ 合成一個 `«世界»`，兩個載體 `«法»`、`«有情»`；同論域關係才有對稱、傳遞、不自反公理。

**存在命題一起考就裝不下（v0.5）。** 加入「七十五法各各實有」（75 條存在部分）、九十八隨眠的存在表（98 條）後，若照舊把全部條目放進一個 5 元素的世界，庫會「不相容」，一切都空真地「證成」。→ 引擎把存在部分拆出來逐條考（見 SKILL 原則 8）。代價：兩條存在部分彼此是否相容，目前不查；「未決」不再是確定的。

**判定變慢的幾個原因與對策。** 每次求解約 5–15 毫秒，題目一多就以分鐘計。已做的：外部原子只改變了的（`Engine._apply`，按位置比較，不用符號作字典鍵——clingo 符號的雜湊很慢）；先看 U 是否已推出否定（是則直接證否）；存在部分只試共用詞最多的前 20 條（`Judge.TOP`，只影響完備性）；證成後不再找反駁。現在三個題庫約 90 秒，結構計算約 75 秒，報告約 5 分鐘。

**相關性過濾的盲點。** 判定與結構計算只拿「與目標共用詞」的存在部分來試（共用詞不計「法類」）。若一條存在命題要經過幾條全稱命題才與目標相連、而與目標沒有共用詞，就會漏掉，結果是「未決」。這只會少證，不會錯證。

**本機裝不了 Lean。** elan 能裝，但下載工具鏈被網絡策略擋（403）。→ 不要重試或繞路；推分支，用 `gh run view --log-failed` 看 Actions。

**隱含的本體命題（v0.4 以前）。** 門的單值、適用條件、關係的類型與對稱、傳遞，以前由引擎默默施加，推導用了它們卻不必寫出。v0.5 起它們是本體結構條目，要寫在「依」的〔本體：…〕裡。`驗證` 推不出時會列出「再補哪些就推得出」。

**有界世界的懸崖。** 命題庫的世界至多 5 個法、2 個有情。一旦寫入「每個善心有十個大地法相應」這類命題，一個心聚就超過 5 個法：求解器會得出「不可能有善心」，或讓有關的題空真地通過。→ 寫「每個 A 有若干 B」一類命題前，先估計需要多少元素；必要時調大 `庫/論域.kosa` 的類別大小（變慢），或改寫成不需要那麼多元素的形式。「證成」「證否」都是有界的，「未決」與「推不出（附反例）」才是確定的。

**舊模組不要用新語義。** 模組一、二、三是非庫模式：門結構內建、不推論域（積類別的元素帶法的門值）。改 `lang.py`、`kb.py`、`engine.py` 時，用 `m.explicit` 分開兩條路；改完跑一遍三個舊模組，`lean/Kosa/Module1.lean` 重新導出後應與原來逐字相同。

**論域推斷。** 一句命題中混用法與有情的詞會報錯；公式中變元的論域由它出現的詞推出，推不出的取預設（法）。跨論域的命題要用公式寫、在量詞處標明（`凡 p 有情、x 法：…`）。

**速度。** `驗證` 約 20 秒，`結構` 約 35 秒，`題庫` 約 15 秒，`報告` 約 2 分鐘。求極小前提用 `Engine.minimize`（二分），不要逐條試刪。

**改名。** 編號出現在：庫的條目與「依」、模組的目標與旁證、`精確化對照.tsv`、Lean 證明（«編號»、«編號成立»）、報告（`kosa/report.py` 中有幾處直接引用編號，如 Lean 導讀引的【業品20】）。改名要一起改。
